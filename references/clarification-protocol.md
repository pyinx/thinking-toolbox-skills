# 第 2 步 问题澄清协议

主 skill 在第 2 步执行：**代理收集各 subskill 的问题 → 归并去重 → 一次性问用户**。
本文件是这一步的完整细则，主 SKILL.md §3 只留摘要。

## 为什么需要这一步

第 4 步有 3~7 个模型各自独立作答。若每个模型都按自己的「关键问题清单」直接问用户，
一次分析会产生 10+ 轮往返，且用户要重复回答实质相同的问题。
本协议把"提问权"从 subskill 收归主 skill——**subskill 只贡献问题，不直接与用户对话**。

## 执行流程（六步）

### 1. 拉取
对 P 中每个 name 读 `<BASE>/subskills/<name>/SKILL.md`（BASE 见主 SKILL.md §0），
记住所属模型。**读取一次即够，第 4 步复用，不再读第二次。**

- 未成功读取 → 不得为该模型编造问题；也不得静默跳过，要在回答里声明"X 模型缺席"。
- 全部模式下读取成本过高 → 直接跳过澄清，改为在第 4 步前"列出所缺假设"。

### 2. 抽取
只取各文件「关键问题清单」小节的条目。**丢弃**「何时不适用」的条目——那是模型边界，不是给用户的问题。

### 3. 归槽（去重的具体做法）

把每个问题映射到一个**槽位**——槽位是问题所索取的信息类型，不是字面文本。
两个问题文字不同但索取同一槽位时，合并为一条。

**固定 12 槽位**：

| # | 槽位 | 典型问法 |
| --- | --- | --- |
| 1 | 目标/成功定义 | "做成什么样算成功？衡量的指标是什么？" |
| 2 | 时间尺度 | "这件事你希望在多久内见效？" |
| 3 | 决策主体 | "这个决定谁拍板？谁会被影响？" |
| 4 | 资源与预算硬约束 | "有多少钱/多少人/多少时间可用？" |
| 5 | 已有事实 vs 已有假设 | "哪些是你确认过的，哪些是推测？" |
| 6 | 风险与失败容忍度 | "最坏情况你能承受到什么程度？" |
| 7 | 取舍序（优先级冲突时先保哪个） | "如果钱和时间只能满足一个，先保哪个？" |
| 8 | 竞争与对手格局 | "谁在同一件事上跟你竞争？" |
| 9 | 不可逆/退出成本 | "如果三个月后要撤销，代价多大？" |
| 10 | 价值观与底线 | "有哪些条件是你无论如何不会接受的？" |
| 11 | 信息可得性 | "你还不知道但能去查到什么？" |
| 12 | 必须做的理由 | "为什么是现在？推迟半年会怎样？" |

槽位可扩展，但**优先复用上表**——槽位越少，归并效果越好。
合并后记录 `<提出该槽位的模型列表>`，供第 4 步标注各模型用了哪几条。

### 4. 准入测试（四项全过才可问，缺一即丢）

| 条件 | 说明 |
| --- | --- |
| a. 多模型会用 | 至少 2 个启用模型会用它做判断。**单个模型专用问题 → 由它内部自问，不问用户** |
| b. 会改结论 | 答案会改变至少 1 个模型的核心判断，或会改变最终主判断 |
| c. 低成本 | 用户能低成本回答：不需要查资料、不需要算账、不需要回忆久远细节 |
| d. 无已有答案 | 槽位内尚无来自上下文或第 3 步取证的答案 |

**"模型想问"不构成提问理由。** 若某问题只有 a 不满足，丢掉它。

### 5. 排序

`信息增益 ≈ 改变结论的可能性 × 结论影响程度 ÷ 回答成本`

- 同增益时，按槽位优先级：**目标/成功定义 > 时间尺度 > 硬约束**。
- 该式不向用户展示，只用于内部排序。

### 6. 截断与提出

- **取前 4 条**（与 AskUserQuestion 的 4 问硬上限对齐）。
- 第 5 条起**不得改问第二轮**——宁可写成显式假设。
- 用 `AskUserQuestion` 一次性提出；工具不可用时降级为编号列表。
- **措辞中性**：禁止"从 X 模型的视角看，应该先搞清…"这种偏向性表述。

## 答案处理

### 回填格式（第 4 步的共享上下文）

```markdown
## 问题澄清（共享上下文）
- Q1 <槽位名>：<问句> → A：<用户答案>
- Q2 <槽位名>：<问句> → 未获回答，采用假设「<假设>」；若实际为 <B>，则结论改为 <C>
- 已知事实基础：（第 3 步结果，无则省略）
```

各模型在第 4 步作答时**直接使用该块**，并在「分析」段内标注用了哪几条
（如"按 Q1 的时间尺度 3 年重算…"），以便用户在第 6 步看到答案如何改变了结论。

### "不知道"怎么办

立即转为显式假设，**不再追问同一槽位**：

```
未获回答 → 采用假设 A；若实际为 B，则结论改为 C
```

假设 A 必须来自用户已给出的上下文的推断，不得凭空造。

### 未获回答的假设怎么呈现

在澄清块中显式列出，不隐藏：

```
- Q3 <槽位>：<问句> → 未获回答，采用假设「<假设>」（若为 <B>，结论改为 <C>）
```

第 6 步的「推翻条件」应包含这些假设被推翻时的后果。

## 防滥用九条

| # | 规则 |
| --- | --- |
| 1 | 四项准入全过才可问；**"模型想问"不构成理由** |
| 2 | 单轮、上限 4 问（对齐 AskUserQuestion 硬上限） |
| 3 | **禁止二次追问**——落选项进入假设 |
| 4 | 单个 subskill 对最终提问**贡献 ≤1 条**，其余转为该模型内部自问 |
| 5 | "不知道"立即转假设，不追问同一槽位 |
| 6 | 时长闸门：澄清**不得让流程停在等待态超过一轮**；用户未答则按假设继续，不阻塞 |
| 7 | 跳过条件从宽（见主 SKILL.md §2.1，5 条按序命中即跳） |
| 8 | 反套话：若合并后的问题读起来像"请依次回答以下 20 题" → 作废重写 |
| 9 | 成本约束：全部模式（27 模型）直接跳过澄清，改为列出所缺假设 |

## 与第 5 步讨论的边界

第 2 步是**向用户提问**，第 5 步是**模型之间交锋**。两者不可混用：

- 第 2 步：主 skill 问用户，问题来自 subskill 的槽位。
- 第 5 步：模型引用对方结论做反驳，用户不参与（细则见 `deliberation-protocol.md`）。
